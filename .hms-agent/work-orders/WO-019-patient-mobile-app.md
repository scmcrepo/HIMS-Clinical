## 1. Objective

A single-codebase patient app that runs on both iOS and Android, covering the 16
screens in the PRD: mobile login with OTP, hospital/profile/branch resolution with
auto-skip, dashboard, consultant browsing, slot selection, booking with
confirmation, appointment management, visit history, the four-tab visit detail,
report viewing, self-registration and settings.

## 2. Scope

### In scope
- New top-level `mobile/` workspace. Not inside `frontend/`, not in the Gradle
  build — same reasoning as `agent-service/`: released on its own cadence, through
  app stores, on its own version clock.
- Typed API client generated by hand against the WO-017/018 contracts, with a
  fixture-backed mock transport so the app is developable and testable before the
  backend endpoints land.
- The resolution state machine (hospital → patient → branch, with auto-skip),
  as pure logic, unit tested.
- Screens, navigation, offline behaviour, secure token storage.

### Explicitly out of scope
- FCM push registration and delivery → WO-020.
- Teleconsultation, payments, prescriptions, family linking → PRD Phase 2/3.
- Store submission, EAS credentials, provisioning profiles. Documented, not run —
  they need the hospital's Apple and Google accounts.

## 3. Current state

Nothing exists. `frontend/` is React 18 + TypeScript + Vite + TanStack Query v5 +
Zustand + Zod + React Hook Form + Tailwind + axios. That stack choice is the main
input to §4.1: the mobile app should be a place a `frontend/` developer can be
productive on day one.

## 4. Design

### 4.1 D2 — Expo (React Native) + TypeScript, not Flutter

The PRD offers "React Native / Flutter". Picking React Native + Expo because:

- The team already writes TypeScript, Zod schemas, TanStack Query and React Hook
  Form in `frontend/`. Validation schemas, error-envelope types and query
  patterns port with edits rather than rewrites. Flutter means a second language
  and a second set of habits for a form-and-list app that does not need it.
- Expo builds iOS in the cloud (EAS), so the hospital does not need a Mac in CI to
  ship an iPhone build.
- Answering approval-doc Q4 (Android / iOS / both): **both, simultaneously**, which
  is the point of the shared codebase. Android is the default test target because
  it is the majority platform for Indian patients.

Tradeoff: Flutter renders complex animation more smoothly on low-end Android.
Irrelevant here — this app is forms, lists and a PDF viewer.

### 4.2 Layering

```
mobile/
  src/
    core/          PURE TypeScript. Zero react-native imports.
                   api client, contracts, resolution machine, validation,
                   formatting, error mapping.
    state/         Zustand stores + TanStack Query hooks
    ui/            design tokens + primitives
    screens/       one folder per PRD screen
    app/           expo-router routes
  __tests__/
```

`core/` having no React Native imports is load-bearing, not tidiness: it means the
booking rules, the auto-skip logic and the response parsing are testable under
plain Node in CI, on every commit, without a simulator. That is the layer where a
bug books the wrong slot or shows the wrong patient, and it is the layer this
session verifies.

### 4.3 The resolution state machine

PRD §3 auto-skips a screen whenever there is exactly one option, at three
consecutive steps. Expressed as data rather than as `if` statements scattered
through three screen components:

```
needsHospitalSelection  = candidates.length > 1
needsPatientSelection   = selectedHospital.patients.length > 1
needsBranchSelection    = selectedHospital.branches.filter(active).length > 1
```

with a `resolve()` that folds the three and returns the next required step or a
completed selection. Reverse navigation (patient taps back from the dashboard)
must re-enter the machine at the last *shown* step, not the last *evaluated* one —
otherwise a single-hospital patient tapping back lands on an empty screen. This is
the sort of thing that is obvious in a state machine and invisible in three
`useEffect`s.

Branch auto-select prefers `isDefault === true` when several are active but only
one is default, matching PRD §3.2 Step 4.

### 4.4 Token handling

- `expo-secure-store` (iOS Keychain / Android Keystore). Never AsyncStorage,
  never Redux-persist: those are plaintext on a rooted device.
- Access 15 min, refresh 7 days, rotating. A single-flight refresh queue so ten
  concurrent 401s produce one refresh, not ten — ten would trip the reuse
  detector from WO-017 and revoke the patient's own chain.
- Biometric re-auth (`expo-local-authentication`) required to open the app when a
  refresh token is present. Cheap, and it is what makes a stolen unlocked phone
  not equal a medical history.

### 4.5 D4 — offline cache excludes clinical data

PRD §10.3 asks to cache profile, upcoming appointments and last 5 visits, and to
queue bookings offline.

Implemented as:
- Cached to encrypted storage: profile summary, upcoming appointments, visit list
  **headers** (date, doctor, type, status).
- **Never** cached to disk: casesheet contents, lab values, radiology findings,
  diagnosis text, attachment bytes. Memory-only, cleared on background.
- Booking is **not** queued offline. A queued booking that fires four hours later
  against a slot that filled in the meantime produces a patient who believes they
  have an appointment and a hospital that has never heard of them. Offline
  booking is a clinical-scheduling promise the client cannot keep; the app shows
  a clear offline state instead.

That last one contradicts PRD §10.3 and is flagged.

### 4.6 D8 — i18n from day one

Every string through `t()` with an English pack shipped. Tamil and Hindi packs are
then a translation task, not a refactor. Answers approval-doc Q5 without paying
for it now.

## 5. Compliance impact

- **Personal data on device:** profile summary and appointment list in encrypted
  storage; clinical data in memory only.
- **Consent:** the `PORTAL_SELF_ACCESS` consent text from WO-017 is displayed and
  accepted in-app at first session, and withdrawable from Settings, which calls
  the withdrawal endpoint and wipes local storage.
- **Cross-border:** none by the app itself. **Crash and analytics SDKs are the
  risk** — a crash reporter uploading a stack trace with a patient name in a
  variable is a cross-border PHI transfer. Decision: no third-party analytics; if
  crash reporting is added later it must be India-region and PII-scrubbed. Not
  installed in this work order.
- **Erasure:** a wipe on logout/withdrawal clears SecureStore and the encrypted
  cache. Server-side erasure is WO-017's job.
- **Screenshots:** Android `FLAG_SECURE` on the visit-detail and report-viewer
  screens; iOS has no equivalent, so this is partial and documented as such.

## 6. Observability plan

Client-side, because a mobile app is invisible from the server otherwise:

- Every request sends `X-Correlation-Id` (UUID v4 per request) so a patient
  complaint maps to a server trace. Structured client log events:
  `app.auth.otp_requested`, `app.auth.session_established`,
  `app.booking.submitted`, `app.booking.failed{code}`, `app.offline.entered`,
  `app.token.refresh_failed`. **No patient identifiers in client logs**, which on
  a mobile device means the OS log buffer any installed app can read on older
  Android.
- No third-party crash SDK (§5). Failures surface as user-visible error states
  with the correlation id shown, so support can find the server-side trace.

## 7. Acceptance criteria

1. `npx tsc --noEmit` clean across `mobile/`.
2. `core/` unit tests green under Node with zero native modules installed.
3. Auto-skip: 1 hospital / 1 patient / 1 branch goes login → OTP → dashboard with
   no selection screens; 2 / 2 / 2 shows all three in order.
4. Back-navigation from the dashboard returns to the last *shown* step.
5. Booking sends an `Idempotency-Key`; the same key is reused on retry of the same
   attempt and regenerated for a new attempt.
6. Tokens are written only via `expo-secure-store` — asserted by a test that fails
   if `AsyncStorage` is imported in `core/auth` or `state/auth`.
7. Slot grid renders full slots as disabled, not hidden (PRD §6c shows them).
8. A date more than 14 days ahead is not selectable.
9. Clinical payloads never reach the persisted cache — asserted by a test that
   inspects what the persister serialises.
10. Every user-facing string resolves through `t()`; a test fails on a literal.

## 8. Risks

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| R1 Backend contract drifts from the hand-written client | High | Medium | Contracts in `core/contracts.ts` are the single definition; a later card generates them from the OpenAPI doc the backend already publishes |
| R2 Double booking from a double tap on a slow network | High | Medium | Idempotency-Key + button disabled through the in-flight window |
| R3 Refresh storm trips reuse detection and logs the patient out | Medium | High | Single-flight refresh queue; explicit test |
| R4 Patient reads a stale cached appointment that was cancelled at the desk | Medium | Medium | Cache shows an "as of HH:MM" stamp and refetches on focus |
| R5 App store review rejects a health app without a privacy policy URL | High | Low | Documented in the release checklist card |

## 9. Open questions — answered, per autonomous mode

1. **React Native or Flutter?** → React Native + Expo. §4.1.
2. **Offline booking queue?** → Not built. §4.5. Overruling PRD §10.3.
3. **Minimum OS versions?** → iOS 15+, Android 8+ (API 26). Covers effectively the
   whole installed base while allowing modern crypto APIs.
4. **Push provider?** → FCM for both platforms (PRD §10.4), deferred to WO-020.
   Note for that work order: an FCM payload must carry only an id and a generic
   title. "Your lab report for HIV screening is ready" on a lock screen is a
   disclosure to whoever is holding the phone.
