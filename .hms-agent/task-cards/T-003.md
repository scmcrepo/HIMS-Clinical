## Implementation notes

- V176 is the next free version — verified, V175 is the highest and there are no duplicates. Re-check before writing in case a colleague took it.
- Tables: agent_api_tokens (id, tenant_id, branch_id NULL, name, token_hash UNIQUE, scopes jsonb, created_by, created_at, expires_at, revoked_at, last_used_at); agent_tool_invocations (append-only audit, surrogate ids only, 7-year retention per confirmed decision); agent_idempotency_keys (key_hash, tenant_id, tool, response_body encrypted, created_at, expires_at).
- Five feature keys seeded for EVERY tenant: AGENT_SCHEDULING_READ, AGENT_SCHEDULING_WRITE, AGENT_BILLING_READ, AGENT_BED_READ, AGENT_TOOLS_READ. Plus AGENT_TOKEN_MANAGE granted to HOSPITAL_ADMIN only. Use the INSERT ... SELECT FROM tenants ... ON CONFLICT DO NOTHING pattern from V158.
- LANDMINE: seeding in a migration only covers existing tenants. TenantService provisioning MUST grant these to tenants created tomorrow. This is the single most common failure mode in this codebase — a feature that works in dev and silently 403s for the next hospital onboarded.
- Create an AGENT role per tenant so agent principals are attributable in role-based reporting, even though authorization actually resolves through token scopes.
- agent_tool_invocations is append-only: document the retention policy and, if your deployment uses a restricted DB role, revoke UPDATE/DELETE on it.
- Index token_hash (unique), tenant_id, expires_at, and idempotency key_hash.
